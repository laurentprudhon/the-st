# The microcoded 68000, and what it would take to run its microcode here

Research for `#76` (the MAME gate) and for the core's fidelity ladder. Everything below is read
from source; each claim is labelled `documented` (a primary source or the code says so),
`derived` (arithmetic over counted facts), `inferred` (a reference implementation's code implies
it) or `unknown`. Tiers follow the project's convention: **T1** hardware-captured, **T2**
hardware-corrected emulator, **T3** emulator-derived. The microcode is **T3** and it is a
transcription, not a measurement — but it is the transcription this project's gate is made from.

## 1. What "the microcode" actually is

`documented` The 68000's control section is a **microcoded** machine: an instruction is not a
handler but a **script of micro-instructions**, each one clock cycle, each selecting ALU sources,
register-file ports and a bus action. MAME's `m68000gen.py` carries that ROM as data and emits C++
from it.

| what | size, counted |
|---|---|
| microcode ROM | **1024 locations, 518 carrying a control word** (17 bits wide), transcribed as 34 masked blocks of 16 (`microcode_base_table`) |
| nanocode ROM | **1024 entries × 96 bits** (three 32-bit words), 529 entries transcribed in 84 masked blocks of 4 (`nanocode_base_table`) |
| named micro-states | **519** of 1024 (`microcode_instruction_names`; 518 non-zero words, 25 `zzz…` placeholders, the rest `-`) |
| decode table | **1528 opcode patterns**, 200 mnemonics (`m68000.lst`) |
| generator | 2569 lines of Python, no dependencies, no MAME headers |

`documented` Each micro-word is: a 9-bit next-address, a 5-bit branch condition (`cbc_names` —
`auz`, `cc`, `n`, `ze`, `enl`, … the hardware's own PAL terms), four nanocode slot selectors, and
the ALU op-field. Each nanocode entry is the ~100 signal bits the generator decodes
(`m68000gen.py:1083-1179`): bus direction and size, the `ftu`/`aob`/`au`/`at` transfers, ALU
source/destination controls, flag masks, the SR transfer, trace and interrupt latches.

`documented` The decode is a **PLA**, not a table lookup by opcode: `a1_pal_test` /`a23_pal_test`
(`:325-478`) turn the instruction register into the microcode entry address, and the ALU row and
column are decoded from the opcode by ~60 bit tests (`:1011-1076`). That is why an instruction's
*shape* (family, size, EA mode) is enough to start a script, and why the same script serves
several opcodes.

### The clock model is two lines of code

```python
source.append("\tm_icount -= 4;")   # a bus cycle          m68000gen.py:2203, 2240
...
elif ci[0] == "istep":              # one micro-state
    source.append("\tm_icount -= 2;")                     # m68000gen.py:2313
```

`derived` So **every micro-state costs 2 CPU clocks and every bus access 4, and a state that
issues a bus access is not also charged its 2** (`istep` is emitted only when the state did not
wait on the bus, `:1741`). Everything the corpus calls `n`/`length` is a count of micro-states;
every `r`/`w`/`t`/`re`/`we` is a `bus_end` state. The whole timing table of the 68000 is *not
tabulated anywhere* — it is the length of each script.

`derived` The prefetch is therefore not a rule but a state: `rrgw1` moves the queue and sets
`m_aob = m_au`, `rrgw2` reads it. `MOVE.w Dn,Dn` is exactly one bus state → 4 clocks, which is the
corpus's `length` for that opcode. A `DIVU` is a chain of `m_icount -= 2` states plus the closing
read, which is why its cost is 76–130 and data-dependent.

### A walk, quoted

`documented` `scripts/microcode-walk.py --op d299` (`ADD.l (An)+,Dn`) prints, in order:

```
// 00f pinl1        m_aob = m_da[ry];  m_au = m_da[ry] + 2;     <- read the first word
                   if(m_aob & 1) { m_icount -= 4; m_inst_state = S_ADDRESS_ERROR; return; }
// 21a pinl2        m_aob = m_au;  m_alub = m_dbin;  m_at = m_au;  m_au += 2;
// 21b pinl3        m_da[ry] = m_au;                            <- the increment COMMITS here
                   if(m_aob & 1) { … S_ADDRESS_ERROR; }
// 1cb roml1        m_aob = m_au; m_ir = m_irc; m_pc = m_au;     <- the prefetch is a state
// 25c roml2        (the closing read)
```

Three facts fall out of that listing, and each one is a failure class in this core today:

1. **the post-increment commits in the state after the first bus cycle**, not before it — an odd
   first word leaves `An` untouched (our `PostIncremented` commits before the access);
2. **`m_pc` is set by the state that starts a fetch** — the exception script saves `m_pc`, so the
   frame's program counter is a *pipeline depth*, decided per script, not per family;
3. **the read of the operand precedes the prefetch**, so a faulting destination keeps a shallower
   `m_pc` than a completed instruction of the same shape.

`documented` The exception entry is a script too — `scripts/microcode-walk.py --state address_error`:

```
// 003 bser1   m_ssw = m_base_ssw | (S ? SSW_S : 0);  m_at = m_aob;  m_ftu = m_sr;  m_au = m_pc;  n 2
// 3a7 bser2   enter supervisor;  m_pc = m_au;  m_au = m_da[16] - 2                            n 2
// 3ca bser3   write m_ftu's high word;  m_au -= 4                                             r/w 4
// 0a2 bser4   write m_pc's high word;  m_ftu = m_ird                                           w 4
…
```

and `SSW_*` is the frame's status word (`m68000.h:108-114`): `DATA 0x01`, `PROGRAM 0x02`,
`S 0x04`, `N 0x08`, `R 0x10`, `CRITICAL 0x20`.

## 2. Our core against it

The correspondence is closer than the code style suggests — we model the same register file.

| MAME | this core | note |
|---|---|---|
| `m_pc` (the PC a frame saves) | `_pc` | "address past the last consumed word" |
| `m_au` (next prefetch address) | `_fetchPointer` | `ReadProgramAsync` sets `_irAddress = address − 2` |
| `m_at` (address of the operand) | the `EaAddressAsync` return | |
| `m_ird` / `m_ir` / `m_irc` | `_ird` / `_ir` / `_irc` | the three-stage queue |
| `m_ftu` / `m_dbout` / `m_dbin` | locals of each handler | **the real difference** |
| `m_decode_table[m_ird]` | `ExecuteAsync(op)`'s `switch` | |
| `m_inst_state` + `m_icount` | `await Cycle(...)` / `await ClocksAsync(n)` | |

`inferred` The gap is not the register file, it is the **lifetime of the temporaries**. In the
microcode `m_ftu`, `m_alub`, `m_at` and `m_dbout` are chip registers that survive across states,
so a script can, say, read the destination into `m_at`, prefetch, then write from `m_dbout` three
states later. Our handlers keep the same information in C# locals inside one `async` method, and
where an instruction needs it across a bus cycle we thread it through a helper. That is why our
bus-cycle *count* matches the corpus while the *order* and the *commit points* do not: a handler
is a shape, not a script.

`derived` Where the core stands on `main` (`91849c7`, measured again for this page):
**279 297 / 317 500 state (88.0 %), 62 of 127 files green, exact-clock 205 161 (64.6 %)**, and
CLK beside it 821 970 / 1 000 060 (82.2 %). The 38 203 failures, split by the first field that
differs (script over `cpu-tests --failures`):

| class | records | what differs |
|---|---|---|
| frame bytes | **27 032** | the exception frame on the stack |
| `a0`–`a6` | **4 842** | the address register after a faulting access |
| `sr` | **3 026** | flags (shifts, `DIV`) |
| `pc` | **1 230** | `STOP` |
| `usp`/`ssp` | **1 115** | `UNLINK` |
| `d0`–`d7` | 632 | |
| RAM, no frame | 326 | |

and the frame class splits further, by which word of the frame differs:

| sub-class | records | measured delta | families |
|---|---|---|---|
| saved PC, low byte | **19 791** | ours **+2** (one word deeper) | `BSR`, `JMP`, and the `.l` ALU/RMW family (`OR.l`, `NOT.l`, `NEGX.l`, `TST.l`, `AND.l`, `MOVE.l`, `CLR.l`, `EOR.l`) |
| saved status word, low byte | **5 211** | ours **+8** = `SSW_N` | `RTS`, `RTR`, `JSR`, `Bcc`, `RTE`, `JMP` |
| other frame bytes | ~2 030 | mixed | `MOVEM`, `MOVEA`, `LINK` |

Two of the classes above are decided by a single line each, and both lines are read straight off the
microcode:

- **`SSW_N` is not "read".** `bser1` composes the frame's status word from `m_base_ssw`, and
  `m_base_ssw` is `SSW_PROGRAM|SSW_R` for a fetch (never `SSW_N`); MAME sets `SSW_N` only on the
  frame's *own* writes, as the nested-fault marker (`SSW_DATA | SSW_N | SSW_CRITICAL`). Our
  `BusStatusWord` sets `0x08` for a fetch fault (`M68000.cs:1166`). One bit; 5 211 records.
  Verified on `RTS` record 002: MAME's status word is `0x4E72`, ours `0x4E7A`.
- **the post-increment commits after the bus cycle.** `pinl3` writes `m_da[ry] = m_au` after
  `pinl1`'s read has completed and before `pinl2`'s read is issued; our `EaAddressAsync` mode 3
  sets the register *before* the access and `SettlePostIncrement` restores it only for a plain
  `MOVE`. The measured deltas confirm per-family commit points rather than a single rule:
  `+4` on 2 667 records (`ADD.l`/`OR.l`/…), `−2` on 1 764 (`ADDX.l`/`SUBX.l`, which step a word at
  a time), `+2` on 411.

`derived` The 19 791 `+2` records are the residual of the prefetch model `#76` landed, and they
are a *placement* statement, not a number: in the `.l` destination-fault scripts the microcode
reads the destination, prefetches, then writes; our handler prefetches at the closing, so at the
fault our `_fetchPointer` is one word further along than MAME's `m_pc`.

## 3. Three ways to use it, and what each buys

### L0 — the microcode as a reading instrument (½ day) — **landed with this page**

`scripts/fetch-m68000-microcode.sh` vendors `m68000.lst` + `m68000gen.py` at the pin (both are
data: 42 KB + 122 KB, BSD-3-Clause, `research/vendor/m68000/`, git-ignored, sha256-checked), and
`scripts/microcode-walk.py` prints any opcode's script or any entry script:

```
scripts/microcode-walk.py --op 80a9             OR.l (d16,An),D0 — the state script, in order
scripts/microcode-walk.py --op 4e75             RTS
scripts/microcode-walk.py --state address_error the group-0 entry script
```

`derived` Cost: two small scripts, no behaviour change, no corpus movement. Buys: every remaining
"why is this clock here" and "what does this frame save" question becomes a two-minute read
instead of a session — including the one datum `LENGTH.md` §6 leaves open (`BCHG`/`BCLR`/`BSET` on
a data register paying 6 or 8: the script has two paths, and the branch condition names which).

### L1 — the microcode as the source of the rules we still have wrong (2–4 days)

Not a table of numbers: **rules taken from the scripts**, each one line of C#, each verified
against the same file it was derived from.

1. `SSW_N` off the fetch path → 5 211 records.
2. The post-increment commits *after* the access that produced it, per family — a `+4` commit in
   `pinl3`-shaped scripts (read-committed), a `−2` commit in the `ADDX` word-at-a-time scripts, and
   the plain `MOVE`'s after-the-write rule kept as a third shape → 4 842 records.
3. The destination read before the write in the `.l` RMW family, with the prefetch between them →
   part of the 19 791.
4. `STOP`'s `pc` (1 230), `UNLINK`'s stack pointer (1 115), `LINK` — each has a script with the
   answer.

Risk: every one of these moves a *convention*, so each must be run against the boot (the `TRAP`
trap of `#76` is the precedent: 11 114 records greened, the boot hung). Reversibility is good —
each is one expression or one call site.

Ceiling: L1 gets the classes the scripts *name*. It cannot get the classes where two records of
the same opcode shape take two different values, which is exactly where `#74` ended (row 57: the
natural rule fixed 23 records and broke 278).

### L2 — the microcode as the engine (multi-session; the only route to 100 %)

Port the model: the two ROM tables as data, the ~100 nanocode signal decodes as methods, the ALU
table (25 ops × byte/long × flag masks) as the chip's ALU, and `ExecuteAsync`'s per-family
handlers replaced by a state loop:

```
m_inst_state = entry from the PLA decode;             // not a switch on opline
while (true) {
    decode the micro-word;                            // next address, condition, slots, ALU
    issue at most one bus access;                     // -> our Cycle(...)
    charge 4 if it touched the bus, else 2;           // -> our ClocksAsync(2|4)
    branch on the condition, or fall through to the next state;
    if (state >= S_first_instruction) { m_ipc = m_pc - 2; m_irdi = m_ird; }
}
```

`inferred` Effort. The data is free (both tables are already transcribed); the work is the
decoder and the ALU. `m68000gen.py` is 2569 lines and about 800 of them are the decode
(`:934-1750`); the C++ helpers it calls are `m68000mcu-head.h` (6144 lines, 158 KB) and are the
ALU/flags/stack semantics we already have in `M68000.cs` — so a prototype can start with *our*
flag code and take only the state ordering from the ROM. A realistic first slice is one family
(`OR.l` to a memory destination, 2 500 records, the whole `+2` and commit-order class) at ~400
lines; the whole instruction set is then mostly data.

`derived` Performance is the thing to price before committing, and it is better than it looks.
Today: 34 311 pops a frame over ~5 400 instructions, i.e. ~6.3 suspensions per instruction. A naive
state loop would suspend per state (~10–40 for `DIV`), which the `#76` measurement already showed
is the expensive shape (`pops_per_frame` moved the mean by 0.78 ms when it changed 40 %). But
**consecutive non-bus states can be collapsed into one wait**: nothing observable happens between
them (no bus access, no interrupt sample inside an instruction), so `n × 2` clocks in one
`ClocksAsync` is the same machine. With that fold, the pops per instruction stay at "one per bus
cycle plus one per idle run" — the same as today.

Cost, honestly: it replaces 2 022 lines of `M68000.Instructions.cs`, it moves both folds, and it
will land the core at MAME's model of *state* as well as clocks, so the CLK report falls to the
MAME-true number (as it already did, 82.2 %) and `TAS`/`TRAPV` stay out. It is the only way to
reach 100 % on the gate, because the remaining 27 032 frame records are "what `m_pc` was at the
1 000th micro-state", and no family-shaped handler has that.

## 4. Recommendation

**Do L0 now, L1 next, and spike L2 on one family before deciding.** Concretely:

1. `scripts/microcode-walk.py` + a paragraph in `tests/680x0/PLACEMENT.md` pointing at it. (§L0)
2. A ticket: *"the microcode's own rules: `SSW_N`, the commit state, the destination read"* — three
   expressions, 10 000+ records, each with the script that justifies it, each boot-checked. (§L1)
3. A spike, in the repo's sense: one family, hand-transcribed script, run against its whole file
   **and** the boot. The question it answers is not "does it pass" (it will) but "how many lines
   per family, and what does it cost `G8`" — the two numbers L2's go/no-go needs.

`derived` Why not straight to L2: the gate's remaining gap is *state*, and the frame class is 71 %
of it, but L1's rules are worth 10 000 records outright (and possibly most of the 19 791) and carry
no risk to the engine; and the fold/`pops` arithmetic above says the *performance* answer for L2 is
not yet measured, only reasoned.

`unknown` One thing this page cannot settle: whether the corpus's frames are MAME's model or the
silicon's. The microcode is transcribed from a die photograph but executed by an emulator, so a
frame convention taken from it is T3 like the corpus — it is the same source, which is why it
agrees, and not independent evidence. (WinUAE's `cputest`, T2, is the only referee; the project
already uses it for `BCD`.)

## 5. Reproduction

```bash
# the two files (BSD-3-Clause, git-ignored, sha256-checked)
bash scripts/fetch-m68000-microcode.sh

# one instruction, or one entry state
python3 scripts/microcode-walk.py --op 80a9          # OR.l (d16,An),D0
python3 scripts/microcode-walk.py --state address_error

# the gate, on this tree
tools/validation-harness/bin/Debug/net11.0/validation-harness cpu-tests --corpus mame \
    --failures /tmp/mame-fail.txt --out /tmp/mame-out.txt
```

The failure-class tables of §2 come from `--failures`, joined against the records' `transactions`
(a `['r', 4, 5, <0x40]` is the vector fetch, i.e. the record framed) and against `final.ssp`
(the frame base). That script is 40 lines of stdlib Python and belongs in `scripts/` with the
walk tool if L1 is taken.
